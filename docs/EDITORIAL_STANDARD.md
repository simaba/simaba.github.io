# Editorial contract · Sima Bagheri's public portfolio

**Current draft: awaiting human editorial acceptance.**

## What this website is

A technically informed personal portfolio, not a product sales funnel. Visitors should distinguish working software, a demonstration, a method, a resource index and a proposal without hunting for a disclaimer. The site should reflect the work of a technical program manager with an interest in evaluation, governance and engineering quality.

## House style

- Write with specific objects and actions. Prefer “checks the internal consistency of a supplied release record” to “empowers trustworthy AI”.
- Keep claims proportional to documented artifacts. Explain what the code accepts, checks, emits or demonstrates. State material limits near the claim.
- Avoid repetitive abstract claims about trust, impact, practical innovation, complexity and accountability. These themes are useful only when followed by technical substance.
- Use a composed, professional first-person voice, without corporate slogans, faux humility, motivational language or generic marketing adjectives.
- Never invent performance figures, customer adoption, employer relationships, security certification, legal applicability, external endorsements or a project’s release maturity.
- Treat tool, prototype, method and resource as materially different artifact types, and record this explicitly.
- Write a short introductory paragraph and distinct project summaries, not a dozen variations on a single sales proposition.
- The repository README is the starting point for verification; it is not proof that implementation or operational outcomes were independently audited.

## Acceptance review (human, not automated)

A reviewer should answer: What does the project contain? What does it not establish? Why is it different from the adjacent project? Can someone familiar with software engineering read this without interpreting promotional jargon? Is anything in the headline, About section, diagram, activity timestamp or footer stronger than its source?

Review every changed visible sentence on desktop and mobile, then compare the project's description, status and limitations with the repository's current README. Reject boilerplate, vague praise, filler qualifiers, slogan clusters, misleading cross-project integration claims and generic “make X Y” heading sequences.

## Maintenance rule

Automatic Github API refreshes can change only verified public metadata (last push, language, star/fork counts). They cannot generate project descriptions, decide which projects to feature or declare maturity. Material editorial revisions require a PR and explicit acceptance. Passing CI's deterministic checks cannot certify literary or professional quality.

## Portfolio positioning
The homepage headline “Systems, tools, and delivery” is intentionally broad: the site represents technical program management and engineering work alongside independently developed utilities, methods and prototypes. The project details carry the specificity rather than asking one AI-governance slogan to speak for the entire professional practice.

The earlier “A score isn’t a release decision” is a defensible *project-level* observation, not the defining statement of this whole portfolio. Retain its distinction between measurements and authorization in the release-governance and evaluation material where it belongs. Do not flatten the work into AI research, safety, consulting, or one cross-repository suite.

This is a candidate editorial direction to be approved by the portfolio owner, not a self-issued acceptance.
